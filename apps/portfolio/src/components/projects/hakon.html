개요

학원 운영자가 출결, 수납, 상담, 공지를 한곳에서 처리하는 관리 시스템이다. 원래는 PHP로 만들어진 레거시였고, 학원 36곳에서 학생 약 7,000명을 관리하고 있었다. 이 시스템을 Next.js·TypeScript 기반으로 새로 설계해 구축했고, 현재 학생 약 500명 규모(일 약 160건 출결)로 베타 운영 중이다.

원비 관리와 역할별 권한 설정. 학원·학생·직원 정보는 가렸다.
좌우로 넘겨 볼 수 있습니다

문제

  • 페이지 이동마다 전체 리로드가 일어나 화면이 깜박였고, 출결처럼 자주 오가는 화면에서 체감이 컸다.
  • 출결은 QR 스캔으로 들어오는데, 관리자 화면은 새로고침해야 반영됐다. 실시간으로 봐야 할 정보가 실시간이 아니었다.
  • 배포는 운영 서버에서 직접 빌드했다. 빌드 동안 서버 리소스를 점유했고, 이미지가 약 2.4GB라 전체 과정이 약 10분 걸렸다.
  • 공통 컴포넌트에 문서가 없고 테스트도 없어, 화면을 고칠 때마다 다른 화면이 깨지는지 손으로 확인했다.

접근과 선택

레거시를 고쳐 쓸지, 새로 만들지가 첫 결정이었다. PHP 코드는 화면과 로직이 섞여 있어 부분 개선으로는 깜박임과 실시간성 문제를 풀 수 없다고 판단했고, 신규 구축을 제안해 주도했다.

선택지 장점 탈락 이유
PHP 위에 부분 개선 당장 비용이 작다 화면 전환 구조 자체가 문제라 근본 해결이 안 된다
React SPA 전환은 매끄럽다 초기 로딩이 길고, 관리 화면이 많아 라우팅·코드 분리를 직접 관리해야 한다
Next.js (채택) 파일 기반 라우팅, SSR·코드 스플리팅이 기본, prefetch로 전환 체감 개선 —
화면 수가 많은 관리 시스템에서는 "라우팅과 코드 분리를 프레임워크가 해주는가"가 유지보수 비용을 결정한다. Next.js를 고른 이유는 성능보다 이쪽이 컸다.

구현

  • 화면 전환. 파일 기반 라우팅 위에 SSR과 코드 스플리팅을 두고, 자주 오가는 경로는 prefetch로 미리 받아 깜박임을 없앴다.
  • 실시간 출결 모니터링. QR 스캔 이벤트를 Socket.io로 받아 관리자 화면에 즉시 반영한다. 새로고침 없이 지금 누가 들어왔는지 보인다.
  • 배포 파이프라인. 서버 직접 빌드를 GitHub Actions에서 Docker 이미지를 만들어 GHCR에 올리고 서버는 pull만 하는 구조로 바꿨다. 실행에 필요한 파일만 이미지에 넣어 크기를 줄였다.
  • 협업 기반. Storybook으로 공통 컴포넌트를 문서화하고 Vitest로 핵심 로직을 테스트한다. 문의 확인이 늦어지는 문제는 Slack을 도입하고 Webhook·GitHub Actions를 연동해 실시간 알림으로 풀었다.
배포 파이프라인 전후. 서버가 빌드하지 않는 구조로 바꿨다.

회고

신규 구축을 결정할 때 레거시의 데이터 구조까지 같이 바꾸지 않은 것은 옳았다. 화면을 먼저 바꾸고 데이터는 그대로 두니 학원 단위로 점진 전환이 가능했다. 아쉬운 점은 테스트를 나중에 붙인 것이다. 처음부터 핵심 로직에 Vitest를 두었다면 재구축 초반의 회귀를 더 빨리 잡았을 것이다.
